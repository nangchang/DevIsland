## 1. 한 줄 진단

> DevIsland는 설계 품질·문서화·테스트 문화가 좋은 프로젝트이나, **"승인 게이트"라는 제품의 존재 이유에 비해 IPC 입구의 보안과 그 주변의 테스트가 가장 약하다.** 보안 하드닝 → 구조 정리 → 기능 확장 순서를 지키면, 병렬 에이전트 시대의 관제탑으로 성장할 기반은 이미 갖춰져 있다.

## 3. 핵심 발견 Top 5

1. **[보안] IPC 입구가 열려 있다.** TCP 리스너가 루프백 제한 없이 모든 인터페이스에 바인딩되고(`HookSocketServer.swift:43`), 레거시 raw JSON 경로는 토큰 검증을 우회한다(`HookEventHandler.swift:43`). 결합 시 LAN의 공격자가 가짜 승인 요청을 노치에 띄울 수 있다. 수정은 각각 몇 줄 수준 — **비용 대비 효과가 가장 큰 작업.**
2. **[보안] 훅 페이로드 전문이 world-readable `/tmp` 로그에 평문 기록**되고 로테이션이 없다 (`devisland_bridge.py:352` 외). 명령 인자 속 시크릿이 노출될 수 있다.
3. **[테스트] 커버리지 밀도가 위험도와 역전.** 플러그인 시스템은 90~100%인데, `HookSocketServer` 2.4%, `BridgeTokenManager` 0%, 정책 엔진의 glob/regex 매칭은 테스트 0개다. 보안 수정의 회귀 방어가 없는 상태.
4. **[구조] AppState god object와 취약한 스레딩 모델.** 2,591줄에 이벤트 분류·큐·결정·표시 상태가 혼재하고, `MainActor.assumeIsolated` 18곳이 런타임 크래시 가정을 분산시켜 놓았다. 정책 평가 SQLite 읽기는 메인 스레드에서 동기 실행된다(최대 5초 블록 가능).
5. **[기회] 반쯤 구현된 기능이 가치로 전환되지 못하고 있다.** PTY 주입(`injection`), 새 세션 실행(`openNewWindow`), 승인 통계 데이터(`approval_decisions`), `approval.decided` 플러그인 이벤트(설계 완료)가 모두 코드에 있지만 사용자 기능으로 연결되지 않았다.

## 4. 통합 실행 순서

네 문서의 권고는 하나의 원칙으로 수렴한다: **보안 → 안전망(테스트) → 구조 → 기능.**

```text
구간          작업                                          출처 문서
────────────────────────────────────────────────────────────────────
v0.12        보안 하드닝 S1~S4 (루프백·토큰·로그)            ①
(2~4주)       + 해당 회귀 테스트 P1 5종을 머지 조건으로        ④
             + 문서 불일치 4건 동기화, CI에 python·shellcheck  ①④

v0.13~0.15   리팩토링 R0~R3 (golden 테스트 → 타입화 →        ②
(~3개월)      AppState 분해 → @MainActor 통일)
             + 기능 H1 6종 (규칙 제안, 진단 뷰, 알림 센터,     ③
               PTY 회신, Quick Launch, 인사이트 플러그인)
             + 메인 스레드 DB 읽기 이동, os.Logger 전환        ①②

v0.16~1.0    리팩토링 R4~R6 (UI 분할, 설치 로직 단일화)       ②
(3~9개월)     + 기능 H2 (Fleet 보드, Git 컨텍스트,            ③
               정책 프로파일, 외부 알림, Provider SDK화)
             + 서명·공증 릴리스(S5), Homebrew cask, 영문 README ①③

v1.0+        원격 승인(보안 트랙 완료에 하드 게이트),          ③
             플러그인 v2 외부 런타임·에셋 생태계, 팀 정책 공유   ③
```

핵심 의존 관계:

- **테스트 P1은 보안 수정의 선행 조건**이다 — 정책 엔진·소켓·토큰의 현재 동작을 고정한 뒤 고쳐야 회귀를 알 수 있다.
- **리팩토링 R3(@MainActor)는 R2(분해) 이후**여야 변경 면적이 안전한 크기가 된다.
- **원격 승인(H3)은 보안 트랙 완료 전 시작 금지** — 현재 IPC 보안 수준에서 원격 표면을 여는 것은 위험하다.

## 5. 유지해야 할 강점

개선 항목만큼 중요한, 바꾸지 말아야 할 것들:

- **플러그인 아키텍처의 격리 원칙** (승인 흐름 불간섭, sanitized DTO, cached rendering) — 설계와 구현 모두 모범적이며, 신규 기능의 기본 확장 경로로 유지
- **브리지의 의도된 fail-open**과 framed 버전 불일치 시 fail-closed — 근거가 코드와 문서에 명시된 좋은 설계 결정
- **행동 기반 테스트 스타일** (`handleMessage` → 응답 JSON 단언) — 리팩토링 내성의 원천
- **문서 허브 구조** (AGENTS.md + `docs/agent/*` + 에이전트 스킬 이중 제공)
- 커밋 규율 (원자성, 한국어 본문, conventional commit)

## 7. 결론

이 프로젝트의 다음 분기는 새 기능이 아니라 **신뢰의 완성**에 써야 한다. 승인 게이트가 네트워크에서 안전하고, 그 동작이 테스트로 고정되고, 코드 구조가 그 위에 기능을 얹을 수 있는 상태가 되면 — H1~H3 로드맵의 기능들은 이미 코드에 있는 기반(PTY 주입, 세션 데이터, 플러그인 플랫폼) 위에서 빠르게 전개할 수 있다. 순서만 지키면 된다: **보안 → 안전망 → 구조 → 기능.**
